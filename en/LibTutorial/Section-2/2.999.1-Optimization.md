<h2 align="center">Reducing the Number of Layouts</h1>

**tModLoader** recalculates the dimensions every tick for an open interface. This means that the `Recalculate` method will be called for every `UIElement` in your interface. <br>

Let's imagine that we have a user interface with *1000* elements, *400* of which are layout elements. This means that `Recalculate` will be called for all *1000* elements every frame. After recalculating the dimensions, the layout of the elements will also change. This means that in addition to *1000* dimension recalculations, we will also have *400* element layout algorithms. As you can imagine, this would make such an interface (and, consequently, this library) unviable. <br><br>

This library solves this problem as follows:<br>
Each layout container remembers:

* Its size during the last call to `Recalculate`.
* The list of elements during the last call to `Recalculate`.
* The dimensions of the elements during the last call to `Recalculate`.
* The container's layout styles.
* The child elements' layout styles.

If:

1. The container's size has not changed.
2. The elements inside the container have not changed.
3. The dimensions of the elements inside the container have not changed.
4. The styles of the container/elements have not changed.<br>

The layout is not performed. <br>

The information above could have been omitted, since the layout container itself does all of this. However, the following problem arises.
Let's consider the following code.

```csharp
UIExStackPanel stackPanel = new();
UIPanel panel1 = new();

// the `Recalculate` method was called for panel1 and all of its descendants
// (which are absent in this example).
// but stackPanel itself does not yet know that a new element has been added to it.
// tModLoader does not provide a way to detect an event of adding an element inside another element.
stackPanel.Append(panel1); 


// at this point `Recalculate()` and `RecalculateLayout()` are called.
// The elements and dimensions are checked. The entire layout cycle is performed.
Append(stackPanel);


// a new element was added to stackPanel. But stackPanel does not know about it.
// nevertheless, it already stores the list of elements from the previous layout.
// on the next tick, `Recalculate` is called for stackPanel.
// the container determines that the element has changed. The entire layout cycle is performed.
UIPanel panel2 = new();
stackPanel.Append(panel2); 
```

<br>

As can be seen in the code above: `stackPanel` recalculated the layout twice, although in fact it only needed to do this once.
There are two solutions to this problem:

<br>

1. Make sure that elements are always added to the layout container **BEFORE** the layout container itself is added to the parent element.
2. Use the `BeginLayoutPreparation` and `EndLayoutPreparation` methods, which will be discussed in detail below.

---

```csharp
public static void BeginLayoutPreparation(UIState state)
	=> _statesPreparationTable.TryAdd(state, _preparationStateMarker);

public static void EndLayoutPreparation(UIState state)
{
    ResetСurrentRecalculateLayoutDelayMsBranch(state);
    ResetLastLayoutInfoForBranch(state);

    if (_statesPreparationTable.TryGetValue(state, out _))
        _statesPreparationTable.Remove(state);

    state.Recalculate();
}
```

* The `BeginLayoutPreparation(UIState state)` method adds the passed `UIState` to the `_statesPreparationTable` table.

* From the moment this method is called, `RecalculateLayout` will not be executed (anywhere in this `UIState`) until `EndLayoutPreparation` is called.

  <br>

* The `EndLayoutPreparation(UIState state)` method removes the passed `UIState` from the `_statesPreparationTable` table.

* From this moment, the effect of `BeginLayoutPreparation` ends and layout works again in this `UIState`.

* `ResetLastLayoutInfoForBranch` forces all descendants of `UIState` to ignore, during the **one** next layout, the information mentioned earlier:

  * Its size during the last call to `Recalculate`.
  * The list of elements during the last call to `Recalculate`.
  * The dimensions of the elements during the last call to `Recalculate`.
  * The container's layout style during the last call to `Recalculate`.
  * The child elements' layout styles during the last call to `Recalculate`.

* `ResetСurrentRecalculateLayoutDelayMsBranch` resets the `СurrentRecalculateLayoutDelayMs` field for all descendants of `UIState`, which will be discussed below. <br><br>

Let's rewrite the previous code using the new information:

```csharp
UIExLayout.BeginLayoutPreparation(this);

UIExStackPanel stackPanel = new();
UIPanel panel1 = new();

// the `Recalculate` method was called for panel1 and all of its descendants
// (which are absent in this example).
// but stackPanel itself does not yet know that a new element has been added to it.
// tModLoader does not provide a way to detect an event of adding an element inside another element.
stackPanel.Append(panel1);


// at this point `Recalculate()` and `RecalculateLayout()` are called.
// `ExamplePanelUI` is present in the `_statesPreparationTable` table.
// element and dimension checks are NOT performed.
// element layout is NOT performed.
Append(stackPanel);


// a new element was added to stackPanel. But stackPanel does not know about it.
// it does NOT store the list of elements after the previous layout,
// because no layout has been performed before.
UIPanel panel2 = new();
stackPanel.Append(panel2);


// `ExamplePanelUI` is removed from the `_statesPreparationTable` table.
// all other layout restrictions are ignored during this relayout
// for the child elements of `ExamplePanelUI`.
// the dimensions are recalculated and all descendants of `ExamplePanelUI` are relaid out.
UIExLayout.EndLayoutPreparation(this); 
```

---

But even in this case, all layout change checks will be performed every frame.<br>
The ideal solution would be to call `UIExLayout.BeginLayoutPreparation(this);` again after calling `UIExLayout.EndLayoutPreparation(this);`.<br>
In this case, the layout container will not even attempt to check the information for changes on its own.<br>
In this case, responsibility for calling the layout lifecycle falls on the end user.<br>
This means that the end user independently tracks when the layout container should relayout the elements.<br>
Then the following methods are called again: `UIExLayout.EndLayoutPreparation(this);`, followed by `UIExLayout.BeginLayoutPreparation(this);`

---

Another problem is stretching the container or its child elements. In this case, the dimensions will change continuously and, as a result, the layout will be recalculated every frame.<br><br>
There are two solutions to this problem:<br>

1. Use the `BeginLayoutPreparation` and `EndLayoutPreparation` tools discussed above. If you know that an element is about to change its dimensions frequently, you can temporarily disable layout.
2. Use `RecalculateLayoutDelayMs`, `SetRecalculateLayoutDelayMsBranch`, or `SetRecalculateLayoutDelayMsState`:<br>

```csharp
public class RecalculateLayoutStateDelay
{
    public int? DelayMs = 0;
}

public abstract partial class UIExLayout : UIExElement
{
    private static readonly System.Runtime.CompilerServices.
        ConditionalWeakTable<UIState, RecalculateLayoutStateDelay> _statesRecalculateDalayMs = new();

    public int RecalculateLayoutDelayMs = 0;

    public static void SetRecalculateLayoutDelayMsBranch(UIElement element, int ms)
    {
        if (element is UIExLayout layout)
            layout.RecalculateLayoutDelayMs = ms;

        foreach (var child in element.Children)
            SetRecalculateLayoutDelayMsBranch(child, ms);
    }


    public static void SetRecalculateLayoutDelayMsState(UIState state, int? delayMs)
    {
        if (_statesRecalculateDalayMs.TryGetValue(state, out RecalculateLayoutStateDelay delay))
            delay.DelayMs = delayMs;
        else
        {
            RecalculateLayoutStateDelay delayNew = new() { DelayMs = delayMs };
            _statesRecalculateDalayMs.Add(state, delayNew);
        }
    }

    public static int? GetRecalculateLayoutDelayMsState(UIState state)
    {
        if (_statesRecalculateDalayMs.TryGetValue(state, out RecalculateLayoutStateDelay delay))
            return delay.DelayMs;

        return null;
    }
}
```

These settings are defined in the `UIExLayout` class. They specify the minimum delay in milliseconds between layouts of a particular element.<br>
That is, after the layout container recalculates the layout, it sets a delay of `N` ms before the next layout.<br>

* If `GetRecalculateLayoutDelayMsState(firstParentState) is not null` - the delay will be determined by this method.
* If `GetRecalculateLayoutDelayMsState(firstParentState) is null` - the delay will be determined by `RecalculateLayoutDelayMs`.
* The `SetRecalculateLayoutDelayMsState(UIState state, int? delayMs)` method allows you to set a delay for a specific `UIState`. If `null` is passed to `delayMs`, the delay for the specified `UIState` is removed.
* The `SetRecalculateLayoutDelayMsBranch` method allows you to set the `RecalculateLayoutDelayMs` delay for the passed element and all of its descendants.
