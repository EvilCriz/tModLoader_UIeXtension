<h2 align="center">Уменьшение количества компоновок</h1>

**tModLoader** пересчитывает размеры каждый тик для открытого интерфейса. Это значит, что для каждого `UIElement` вашего интерфейса будет вызываться метод `Recalculate`.
<br>

Представим, что у нас есть пользовательский интерфейс с *1000* элементов, *400* из которых - элементы компоновки. Это означает, что каждый кадр для всей *1000* элементов будет вызываться `Recalculate`. А после пересчета размеров также будет меняться компоновка элементов. Значит, что помимо *1000* пересчетов размеров, у нас также будет *400* алгоритмов компоновки элементов. Как вы понимаете, это сделает данный интерфейс (и, как следствие, данную библиотеку) нежизнеспособной.
<br><br>

Данная библиотека решает эту проблему следующим образом:<br>
Каждый контейнер компоновки запоминает:
- Свой размер при последнем вызове `Recalculate`.
- Список элементов при последнем вызове `Recalculate`.
- Размеры элементов при последнем вызове `Recalculate`.
- Стили компоновки контейнера.
- Стили компоновки вложенных элементов.

Если:
1. Размер контейнера не изменился.
2. Элементы внутри контейнера не изменились.
3. Размеры элементов внутри контейнера не изменились.
4. Стили контейнера/элементов не изменились.<br>

Компоновка не выполняется.
<br>

Информацию выше можно было бы не писать, ведь это все делает сам компоновщик. Но тут возникает следующая проблема.
Представим следующий код.

```csharp
UIExStackPanel stackPanel = new();
UIPanel panel1 = new();

// для panel1 и всех его потомков (которых в этом примере нет) вызвался метод `Recalculate`.
// но сам stackPanel пока ничего не знает о том, что в него добавлен новый элемент.
// tModLoader не дает возможности узнать о событии добавления элемента внутрь другого.
stackPanel.Append(panel1); 


// в этот момент вызывается `Recalculate()` и `RecalculateLayout()`. Проверяются элементы и размеры. Выполняется весь цикл компоновки.
Append(stackPanel);


// в stackPanel добавлен новый элемент. Но stackPanel об этом не знает.
// тем не менее он уже хранит список элементов после предыдущей компоновки.
// при следующем тике у stackPanel вызывается `Recalculate`.
// контейнер определяет, что элемент изменился. Выполняется весь цикл компоновки.
UIPanel panel2 = new();
stackPanel.Append(panel2); 
```

<br>

Как видно в коде выше: `stackPanel` пересчитал компоновку дважды, хотя фактически ему нужно было это сделать только 1 раз.
Решения у данной проблемы два:

<br>

1. Следить за тем, чтобы элементы всегда добавлялись в компоновщик **ДО** того, как сам компоновщик будет добавлен в родительский элемент.
2. Использовать методы `BeginLayoutPreparation` и `EndLayoutPreparation`, о которых подробно поговорим ниже.

----

```csharp
public static void BeginLayoutPreparation(UIState state)
	=> _statesPreparationTable.TryAdd(state, _preparationStateMarker);

public static void EndLayoutPreparation(UIState state)
{
    ResetСurrentRecalculateLayoutDelayMsBranch(state);
    ResetLastLayoutInfoForBranch(state);

    if (_statesPreparationTable.TryGetValue(state, out _))
        _statesPreparationTable.Remove(state);

    state.Recalculate();
}
```

- Метод `BeginLayoutPreparation(UIState state)` заносит переданный `UIState` в таблицу `_statesPreparationTable`.
- С момента вызова данного метода `RecalculateLayout` не будет выполнен (нигде в данном `UIState`) до вызова `EndLayoutPreparation`
<br>

- Метод `EndLayoutPreparation(UIState state)` убирает переданный `UIState` из таблицы `_statesPreparationTable`.
- С этого момента действие `BeginLayoutPreparation` прекращается и компоновка снова работает в данном `UIState`.
- `ResetLastLayoutInfoForBranch` заставляет всех потомков `UIState` игнорировать, при **одной** следующей компоновке, информацию о которых упоминалось ранее:
  - Свой размер при последнем вызове `Recalculate`.
  - Список элементов при последнем вызове `Recalculate`.
  - Размеры элементов при последнем вызове `Recalculate`.
  - Стиль компоновки контейнера при последнем вызове `Recalculate`.
  - Стили компоновки вложенных элементов при последнем вызове `Recalculate`.
- `ResetСurrentRecalculateLayoutDelayMsBranch` сбрасывает для всех потомков `UIState` поле `СurrentRecalculateLayoutDelayMs`, о котором будет идти речь ниже.
<br><br>

Перепишем предыдущий код с учетом новой информации:
```csharp
UIExLayout.BeginLayoutPreparation(this);

UIExStackPanel stackPanel = new();
UIPanel panel1 = new();

// для panel1 и всех его потомков (которых в этом примере нет) вызвался метод `Recalculate`.
// но сам stackPanel пока ничего не знает о том, что в него добавлен новый элемент.
// tModLoader не дает возможности узнать о событии добавления элемента внутрь другого.
stackPanel.Append(panel1);


// в этот момент вызывается `Recalculate()` и `RecalculateLayout()`.
// `ExamplePanelUI` находится в таблице `_statesPreparationTable`.
// проверка элементов и размеров НЕ выполняется.
// компоновка элементов НЕ происходит.
Append(stackPanel);


// в stackPanel добавлен новый элемент. Но stackPanel об этом не знает.
// он НЕ хранит список элементов после предыдущей компоновки.
// так как никакой компоновки до этого не было.
UIPanel panel2 = new();
stackPanel.Append(panel2);


// `ExamplePanelUI` удаляется из таблицы `_statesPreparationTable`.
// все другие ограничители компоновки игнорируются при этой перекомпоновке
// для дочерних элементов `ExamplePanelUI`.
// происходит пересчет размеров и перекомпоновка всех потомков `ExamplePanelUI`.
UIExLayout.EndLayoutPreparation(this); 
```

----

Но даже в этом случае все проверки на изменения компоновки будут проводиться каждый кадр.<br>
Идеальным решением будет после вызова `UIExLayout.EndLayoutPreparation(this);` повторно вызывать `UIExLayout.BeginLayoutPreparation(this);`.<br>
В этом случае компоновщик не будет даже пытаться проверять изменения информации самостоятельно.<br>
В этом случае ответственность за вызов жизненного цикла компоновки ложиться на конечного пользователя.<br>
Это значит, что конечный пользователь самостоятельно отслеживает, когда компоновщик должен осуществить перекомпоновку элементов.<br>
Тогда вновь вызываются метод: `UIExLayout.EndLayoutPreparation(this);`, а затем вновь `UIExLayout.BeginLayoutPreparation(this);`

----

Еще одна проблема: растягивание контейнера или его дочерних элементов. В этом случае размеры будут меняться все время, и, как следствие, каждый кадр будет происходить перекомпоновка.<br><br>
Решения у данной проблемы два:<br>
1. Использовать инструменты `BeginLayoutPreparation` и `EndLayoutPreparation` о которых мы говорили выше. Если вы знаете, что сейчас элемент будет часто изменять размеры, вы можете временно отключить компоновку.
2. Использовать `RecalculateLayoutDelayMs`, `SetRecalculateLayoutDelayMsBranch` или `SetRecalculateLayoutDelayMsState`:<br>
```csharp
public class RecalculateLayoutStateDelay
{
    public int? DelayMs = 0;
}

public abstract partial class UIExLayout : UIExElement
{
    private static readonly System.Runtime.CompilerServices.
        ConditionalWeakTable<UIState, RecalculateLayoutStateDelay> _statesRecalculateDalayMs = new();

    public int RecalculateLayoutDelayMs = 0;

    public static void SetRecalculateLayoutDelayMsBranch(UIElement element, int ms)
    {
        if (element is UIExLayout layout)
            layout.RecalculateLayoutDelayMs = ms;

        foreach (var child in element.Children)
            SetRecalculateLayoutDelayMsBranch(child, ms);
    }


    public static void SetRecalculateLayoutDelayMsState(UIState state, int? delayMs)
    {
        if (_statesRecalculateDalayMs.TryGetValue(state, out RecalculateLayoutStateDelay delay))
            delay.DelayMs = delayMs;
        else
        {
            RecalculateLayoutStateDelay delayNew = new() { DelayMs = delayMs };
            _statesRecalculateDalayMs.Add(state, delayNew);
        }
    }

    public static int? GetRecalculateLayoutDelayMsState(UIState state)
    {
        if (_statesRecalculateDalayMs.TryGetValue(state, out RecalculateLayoutStateDelay delay))
            return delay.DelayMs;

        return null;
    }
}
```

Данные настройки определены в классе `UIExLayout`. Они отвечают за минимальную задержку в миллисекундах при компоновке определенного элемента.<br>
То есть после того как компоновщик пересчитал компоновку, он устанавливает задержку перед следующей компоновкой в размере `N` ms.<br>
- Если `GetRecalculateLayoutDelayMsState(firstParentState) is not null` - задержку будет определять этот метод.
- Если `GetRecalculateLayoutDelayMsState(firstParentState) is null` - задержку будет определять `RecalculateLayoutDelayMs`.
- Метод `SetRecalculateLayoutDelayMsState(UIState state, int? delayMs)` позволяет установить задержу определенному `UIState`. Если в `delayMs` передан `null` - убирает задержку для переданного `UIState`.
- Метод `SetRecalculateLayoutDelayMsBranch` позволяет установить задержку `RecalculateLayoutDelayMs` переданному элементы и всем потомкам.
